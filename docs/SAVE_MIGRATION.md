# P0-2 セーブ形式と段階的移行方針

起点main：`19104a60c5fbcc605a9751ede20d0cf290e354cd`。本書は実コードと[P0-1の実形式fixture](../tests/fixtures/README.md)に基づく。**現行の実装**と**将来変更時の方針**を区別する。P0-3以降は未実装。

## 1. 現在の契約と版の意味

| 対象 | 現行契約 | P0-2の扱い |
|---|---|---|
| 自動保存 | `life-sim-modern-v1`、値はraw GameStateのJSON | キーと形を維持。Appはraw正規化を呼ぶ |
| 3スロット | `life-sim-modern-v1-slot-1`〜`-3` | キー、独立性、上書き確認を維持。値はexport形式 |
| ファイル/スロット | `{ format: "life-simulator", formatVersion: 1, state: {...} }` | formatは製品の識別、formatVersionは外側の仕様。形/値を維持 |
| state | `version: 1` | 内側の状態仕様。リリース版v2/v3とは別。今回は増やさない |
| 世界 | worldIdはmodern/coastal、内容は公開JSONから取得 | 世界を暗黙に切り替えない。ルールの版はまだ保存しない |
| 決定性 | 継続seed、birthSeed/initialIdentityChoice、pending/queue/scheduled等を保存 | 再抽選・月の再処理・乱数ストリーム分割なし |

`src/saveFormat.ts` の3つの定数が現在の対応値を持つ。外側と内側の版は目的が異なるため同時に増やす前提にしない。単なるコード分割や既存契約内の補完/検証強化で版を上げない。

P0-1のfixtureは変更せず、同じraw状態およびenvelopeを読み込み、再エクスポートしたオブジェクトが一致することを検証する。整形やプロパティ順の違いを保存意味の変化とみなさない。失敗時の原本については文字列そのものを保持する。

## 2. 現在のロード境界（実装済み）

1. JSONファイル/スロットは `importSave` で文字数上限5,000,000とJSON構文を検査する。ファイルUIもサイズ上限を検査する。自動保存の読込はAppから `normalizeGameState` へ進むため、この文字数上限の経路とは別である。
2. `unwrapSave` はformat/formatVersion/stateのいずれかが最上位にあればenvelopeとして扱う。3項目が対応する値/形であることを要求し、最上位versionとの混合は拒否する。別ゲーム、未来版、項目欠落、配列/null stateをrawへフォールバックさせない。
3. envelopeのstateまたはraw stateを `normalizeGameState` へ渡す。ここでも予約フィールドformat/formatVersion/stateの混入を拒否するため、自動保存経路での識別回避や入れ子envelopeも通さない。
4. 既存の再帰検査（非有限数、深さ30超、不正キー等）、必須値検査、既定値補完、旧名称等の変換、状態の整合検査を行う。relationsの範囲/参照検査を追加した。
5. すべて成功した状態だけを呼び出し側へ返す。import/正規化/形式識別自体はlocalStorageを書かず、入力を変更せず、ゲーム時間を進めない。
6. UIは成功後に確認を経て復元する。初期ロード失敗時のsaveBlockedとPWA更新保護は既存のまま使う。

現在の正規化には既定値補完と検証が混在している。今回すべてを厳密なschema/新しい移行pipelineへ書き換えず、形式識別を独立させる範囲に留めた。公開ゲームAPIの全操作に入力検証を追加したわけでもない。

## 3. 値の欠落・型・範囲に対する方針

| 入力 | 現在の処理と判断 | 選択理由・限界 |
|---|---|---|
| version/month/seed/stats/history等の核となる必須値が不正 | 既存検査により拒否 | 別の人生・時刻・乱数状態へ黙って置換しない |
| 対応済みの不足フィールド | 既存初期値・normalizeSocial/Progression等で補完 | 現行が受理する旧保存の互換性を維持。birthSeed不明はnull、属性選択不明は空オブジェクト |
| 旧方針study/social/health | learning/relationships/wellnessへ既存変換 | 既に実装された別名。架空の旧versionの追加ではない |
| degree/studyPath/timeline等の不足 | 現行の条件付き補完を維持 | 旧学歴/履歴の実装済み規則。推定値が元の事実そのものとは限らない |
| 存在するrelations要素の型不一致・非有限値 | 拒否（既存の有限値/形検査） | 文字列の数値化等をしない |
| closeness/trustが0〜100の範囲外 | **拒否**（K5修正） | clampすると入力破損を隠し、関係と以後の分岐が変わる。端点・小数は受理 |
| relations.idがpeopleに存在しない | **拒否**（K6の限定修正） | 人物や関係を生成/削除する根拠がなく、進行結果が変わる |
| 未知フィールド | 予約したenvelope項目を除き既存どおり保持 | 将来/利用者付与の無関係な拡張を一括削除しない。envelopeの無関係なmetadataは状態へ混ぜない |
| people/relations等が欠落、または一部の型が不正 | 現行normalizerに既定値補完/フォールバックがある | 「すべての型不一致を拒否済み」とはしない。明示null/不正型と欠落の全体的な区別は未決。互換性資料なしで一括厳格化しない |

この表は既存バリデータの全フィールド一覧ではない。具体的な検査はengineを参照。特にromance、全タイムスタンプ、全リンク/親子/婚姻整合まで網羅したschemaを今回導入していない。

将来、新しい必須値を加える際は「欠落しても安全に同等の継続ができる既定値」と「推定できない履歴/人物事実」を区別する。不正な明示値を不足値と同一視して埋めず、拒否または明示移行として定義・テストする。この一般原則を適用して既存の曖昧なフォールバックを変える場合は、対応する実データと影響調査を先に行う。

## 4. K5〜K7の判断と参照整合性

| 問題・再現入力 | 危険性 | 採用した処理 | 互換性への配慮 |
|---|---|---|---|
| K5：fixtureのrelations[0].trust=150（同様にcloseness<0等） | 範囲外の関係で判断/表示が変わる | 拒否。正規化によるclampや移行はしない | 正規の更新は両値を0〜100に制限する。0/100、小数、故人への記録は有効 |
| K6：relations[0].id='not-a-person' | 参照先がなく、生活/表示/選択の対応が失われる | people集合への存在確認に限って拒否 | 生存者だけに絞らず故人も許す。人物ごとのrelation必須や双方向一致は要求しない |
| K7：rawの全フィールドとformatVersion:99のenvelopeを混合 | 未対応形式がraw v1として検査を回避 | 対応envelope/rawを先に識別し、未対応/欠落/混合を拒否 | 正規のraw自動保存と実際のv1 exportは維持。形式を混ぜた手編集データを正当な旧形式とみなさない |

NPC参照は一律に「peopleに存在しない文字列はすべて破損」としてはいけない。

- NPCのpartnerId/spouseIdや子のparentIdsはPCを `player` として参照する。子の親が不明な場合の `unknown` も実コードにある。
- 関係や婚姻は現行の更新途中/旧データで片側だけが残る可能性があり、NPCリンクには過去のsince等がある。故人へのrelationを削除してはいけない。
- pending.personId、npcLinks.a/b、各partnerId/spouseId/parentIdsの全参照と双方向整合を厳格化するには、実際の生成経路と旧保存の調査が必要。今回は自動修復・削除・拒否を追加しない。
- queueのIDを現在のJSONに存在するものだけへ削ると、途中保存からの継続が変わり得る。未知のイベントIDの移行はコンテンツ版と併せて将来決定する。

これらは保留であり、関係モデルの刷新（P3-1）、NPC生活（P3-2）、履歴設計（P0-3/P1-2）を実装したことにはしない。

## 5. 将来の段階的移行（方針・未実装）

実在する新形式が必要になったときに、その形式と直前のサポート版を明示して変換を追加する。存在しないv0/v2のfixtureやmigration関数を予め作らない。

1. 対応する入力版を識別し、変更前のJSON/バックアップを保持する。未対応の未来版はそこで停止する。
2. 旧状態の前提を検証する。実在する不足フィールドの補完はその版の契約に従う。
3. 版N→N+1を副作用のない変換として実行する。各段階の中間結果を検証し、複数段階が必要なら順番に進める。途中失敗時に永続保存しない。
4. 現行の最終版へ到達後、全領域・参照の検査を通す。移行の再適用、保存往復、再現性を確認する。
5. 成功した結果だけを復元し、既存の保存経路で書き出す。以前のアプリへ戻した場合に読めるかを明記する。

責務は、形式識別/JSONを保存層、各領域の値の意味と変換を領域の所有者、移行順序と全体検証をロード境界、原本保護と置換確認を保存/UIの呼び出し側が持つ。GameStateの分割案は [STATE_ARCHITECTURE](STATE_ARCHITECTURE.md) を参照する。

必要な将来の型・registry・adapterの方式はまだ決めない。数値のclamp、未知人物の生成、過去の死亡月推定、出生seedの復元等を「移行」の名で暗黙に行わない。

## 6. 失敗時の原本保護と再保存

- importSave、loadSlot、normalizeGameStateは読込/検査のみで、storageへの書込権限を持たない。新規入力が失敗してもアクティブな状態・自動保存・他のスロットを置換しない。
- Appの初期ロード失敗はsaveBlockedを維持し、エラーを表示して自動上書きを止める。PWAの「保存して更新」も原本保護中は止める。
- JSON/スロットの復元は成功後の明示確認、新しい人生はユーザーの明示操作を必要とする。失敗の代償としてlocalStorage.clear/removeを呼ばない。
- 正規の現行v1は再保存しても同じキー/formatVersion/state versionのまま。同じルール・内容で保存再開した結果は連続実行と一致する。スロット1〜3の独立性を維持する。
- 現在の既定値補完を受けた古いraw状態は、読み込んで再保存すると補完済みのv1になる。出生seed等の不明値はそのまま。元の不足したJSONとのバイト一致は約束しない。
- 将来のversionを上げた保存は旧アプリで読めると保証しない。現行アプリが未来形式を拒否することと、down migrationの実装は別である。

今回、既存の破損保存保護に対し、範囲外JSONインポートで現在の人生/自動保存/スロットが不変であること、参照不整合rawの保護と有効JSONからの明示復元をブラウザで追加検証する。書込失敗、容量超過、複数タブの競合、OSが保存領域を削除する問題まで解決したものではない。外部JSONバックアップは引き続き必要。

## P0-3での互換拡張

任意の `randomStreams` と `worldHistory` を追加し、存在する場合だけ各version/内容を検査する。欠落した旧保存を拒否せず、欠落のまま読み込む。世界履歴は新たな事実だけを記録し、旧ログから過去を生成しない。乱数は全面適用を保留し、現行ゲームは単一seedの消費規則を維持する。詳細は [RANDOM_AND_HISTORY](RANDOM_AND_HISTORY.md)。旧アプリは新しい履歴の追記/検査を行わないため、版を戻して進行した場合の新履歴の完全性は保証しない。

## P1-1 死亡月の互換性

Personへ任意のdeathMonthを追加した。新たに生存→死亡となった時点の月だけを記録する。既存の故人に値がなければ欠落のまま（nullも不明として許容）とし、現在月や旧文章から推定しない。表示は死亡時年齢不明。既知の死亡月は整数、出生月以上・現在月以下、死亡した人物に限り受理する。生存者は従来どおり現在月から加齢する。人物・relations・旧historyは消さない。NPC更新/後処理が既に死んだ人物を書き換えないようguardする。健康・経済・職業・成長・乱数の係数は変更しない。

## P1-2 知識境界

新しいNPC事実はworldHistoryに保存し、明示的な公開時だけpcKnowledgeと任意のLogEntry.worldEventIdを付ける。欠落した旧履歴を再分類・削除せず、知識や内部の過去を捏造しない。保存再開時に再公開しない。公開ルールと未対応範囲は [KNOWLEDGE_BOUNDARY](KNOWLEDGE_BOUNDARY.md) を参照。保存ファイルには内部履歴も含み、UIでの非公開とファイルの秘匿性は別である。

## P2-1 任意の人物能力観測

`capabilities` version 1を追加。外側のformatVersion/state.version、キー、スロット形式は維持する。`stats`/`traits`/教育職業履歴は移動・削除しない。旧セーブの欠落はそのまま維持し、最初の実活動時から`legacyBaseline: true`で観測を開始する。導入前技能は未知。値域0..100、観測年月、公開資質のtraits参照、観測量の非負有限値を検証し、違反は拒否する。元データ保護は既存のインポート経路に従う。詳細は[CAPABILITIES](CAPABILITIES.md)。

## P2-2 任意の時間拡張

任意の`timeBudget` version 1と`focusPlan`を追加。旧fixtureは補完なしで一致する。月の確保時間・活動・計画状態を保持し、選択待ち/再開で二重実行しない。時間の合計720以下、月の上限、非負有限値、強度と実行時間の対応を検証し、不正な拡張は拒否する。旧途中月の過去時間は不明であり推定しないが、既存の月1回制限は維持する。外側の版/キー/3スロットは変更しない。旧アプリへの逆移行（時間ルールの実行・検証）は保証しない。詳細は[TIME_AND_ACTIONS](TIME_AND_ACTIONS.md)。

## P2-3 実参加時間

timeBudget.participationは任意のschool/work実参加時間。旧予算には補完せず、次の月開始から記録する。非負有限値で確保済み時間以内を要求し、不正値は拒否。技能の既得値/practiceは変更しない。外側の版・キー・3スロットは維持。同一新ルールで保存再開一致を保証し、旧ルールとの合否一致は保証しない。

## P3-1 方向別関係

任意relationshipModel version1を追加し、旧relationsをPC側の親密さ/信頼の正本として保持する。逆方向の感情は補完しない。不明軸はnull、導入後の交流で中立基準から観測を開始。旧保存の読込/再保存では拡張を生成しない。方向の重複・不存在人物・自己参照・範囲外・未来時刻を拒否。故人のedgeも削除しない。詳細はRELATIONSHIPS_V3.md。

## P3-2 NPC行動と確認済み情報

任意npcAgency version1（導入月/seed/ストリーム由来、目標/更新月/時間/疲労/直近行動、既に公開されていた人物情報とリンク）を追加。旧状態のロードでは補完しない。最初の新しい実行境界から記録し、過去のNPC目標や更新月を推定しない。人物を一括初期化しない。目標・時刻・範囲・参照を検証して不正値を拒否する。ID予約語の拒否は正規生成された旧NPC IDには影響しない。

randomStreamsは存在すれば継続、なければ新判断の初回使用時の現在seedから開始。従来の健康/イベント等の全面切替は行わない。knownPeopleには導入時に既に公開されていた生活情報と観測月/イベント開始IDを保持し、古い既知通知で最新の既存表示を巻き戻さない。新しい私的変化はPCが知った後だけ投影する。未知の旧感情/旧目標を復元したとは扱わない。形式/キー/3スロットは維持。
